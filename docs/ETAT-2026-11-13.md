## 1. Le verdict

Le 12/11, l'export hebdomadaire de la base produisait **un fichier vide** : le workflow
partait sur `~/.prevensante-sauvegardes` (un dossier qui n'existait pas) et ne récupérait
que la structure, sans les lignes. C'était le défaut le plus grave du projet — une
décision d'exploitation validée (A10) reposait sur une copie qui n'existait pas.

Deux choses ont été faites depuis :

1. **L'export est réparé** et produit bien structure + données.
2. **La restaurabilité est prouvée** : le dump produit est rejoué dans une base neuve,
   table par table, et comparé à l'instance réelle. L'opération tourne **chaque semaine
   dans la CI**, avant la publication de l'artefact.

Un fichier de sauvegarde dont personne n'a vérifié qu'il se rejoue n'est pas une
sauvegarde. C'est maintenant vérifié, automatiquement, et le résultat est publié.

## 7. Un point signalé puis résolu : le secret de déploiement Vercel avait expiré

Constaté le 13/11/2026 en poussant ce contrôle, le job **« Déploiement en production »**
échouait :

```
Error: The token provided via the `--token` option is not valid.
```

**Ce n'était pas une régression** : le même job était vert le 12/11 à 13:44 (1 min 06 s). Le
secret `VERCEL_TOKEN` du dépôt avait été révoqué ou avait expiré entre-temps.

**Pendant ce temps, rien n'était cassé pour l'utilisateur** : l'application en ligne
répondait toujours (`https://prevensante.vercel.app` → HTTP 200) et **aucun code applicatif
n'avait changé** — les commits du 13/11 portent sur l'outillage, les tests et la
documentation. Seule la mise en production automatique des prochains pushs était
suspendue.

**Résolu le jour même.** Un token personnel Vercel dédié, nommé `prevensante-ci`, portée
« Full Account » et expirant le 13/11/2027, a été créé depuis le tableau de bord et posé
comme secret chiffré `VERCEL_TOKEN` du dépôt. Le job est repassé au vert :

| Job | Résultat |
|---|---|
| Verification de la base Supabase reelle | ✅ succès |
| Typage, SQL et recette E2E | ✅ succès |
| **Deploiement en production (Vercel)** | ✅ **succès** |

*Un piège rencontré, consigné pour ne pas le rediscovering : un secret écrit depuis
PowerShell peut être pollué par un caractère BOM invisible, que Vercel refuse avec
`Must not contain: "﻿"`. Le token doit être transmis sans BOM — c'est fait, et vérifié
contre l'API Vercel avant de relancer la CI.*

### Relier le dépôt Git à Vercel : **écarté le 13/11/2026**

Une option de repli avait été envisagée : connecter le dépôt GitHub au projet Vercel
(« Connected Git Repository »), pour que Vercel déploie même si le secret de la CI
tombait. **Le commanditaire a écarté cette option** : l'application Vercel sur GitHub
donne à Vercel des droits sur le dépôt, et ce doublon n'est pas nécessaire.

> État vérifié après l'essai : *« This Project is not connected to a Git repository. »*
> Aucune permission n'a été donnée, aucun réglage modifié.

**Ce qui reste à surveiller** : le token `VERCEL_TOKEN` expire le **13/11/2027**. Le
renouveler prend une minute (tableau de bord Vercel → Tokens → « Continue with GitHub »
→ code reçu par e-mail → puis poser le secret via
`gh secret set VERCEL_TOKEN --repo sawadogosoumaila234-dot/prevensante --body "<valeur>"`).

**Si le token expire un jour**, le site reste en ligne — c'est ce qui s'est passé le
13/11 — mais les prochains pushs applicatifs ne sont plus mis en production. La parade est
alors de redéployer manuellement depuis Vercel (onglet Deployments → … → Redeploy) ou de
renouveler le token.

## 8. Le point à retenir

Une sauvegarde n'est pas un fichier qu'on a produit : c'est un fichier **qu'on a prouvé
rejouer**. La preuve tourne désormais chaque semaine dans la CI, avant la publication de
l'artefact. Le jour où la base devra être reconstruite, ce ne sera pas une inconnue : ce
sera un test déjà vert.
