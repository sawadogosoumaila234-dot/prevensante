## 1. Le verdict

Le 12/11, l'export hebdomadaire de la base produisait **un fichier vide** : le workflow
partait sur `~/.prevensante-sauvegardes` (un dossier qui n'existait pas) et ne récupérait
que la structure, sans les lignes. C'était le défaut le plus grave du projet — une
décision d'exploitation validée (A10) reposait sur une copie qui n'existait pas.

Deux choses ont été faites depuis :

1. **L'export est réparé** et produit bien structure + données.
2. **La restaurabilité est prouvée** : le dump produit est rejoué dans une base neuve,
   table par table, et comparé à l'instance réelle. L'opération tourne **chaque semaine
   dans la CI**, avant la publication de l'artefact.

Un fichier de sauvegarde dont personne n'a vérifié qu'il se rejoue n'est pas une
sauvegarde. C'est maintenant vérifié, automatiquement, et le résultat est publié.

## 6. Comment rejouer les contrôles

```bash

npm run base:restaurer -- --fichier <le.sql>             # prouve qu'il se rejoue
npm run base:verifier                                     # instance réelle : 15 contrôles RLS
npm test                                                  # 34 tests du routeur
```

Et pour l'export hebdomadaire, sans rien lancer : l'onglet **Actions** du dépôt montre
chaque exécution, son durée, et le verdict du test de restauration.

## 7. Un point à signaler : le secret de déploiement Vercel a expiré

Constaté le 13/11/2026, en poussant ce contrôle. Le job **« Déploiement en production »**
de la CI échoue :

```
Error: The token provided via the `--token` option is not valid.
```

**Ce n'est pas une régression** : le même job était vert le 12/11 à 13:44 (1 min 06 s). Le
secret `VERCEL_TOKEN` du dépôt a été révoqué ou a expiré entre-temps.

**Ce que cela ne touche pas :** l'application en ligne répond toujours
(`https://prevensante.vercel.app` → HTTP 200), et **aucun code applicatif n'a changé
aujourd'hui** — les commits du 13/11 portent sur l'outillage, les tests et la documentation.
La production est donc celle qui était en service ce matin, et elle est saine.

**Ce que cela touche :** le prochain push qui modifie l'application ne sera **pas** mis en
production automatiquement. C'est la décision « la production suit les pushs » (11/11/2026)
qui ne s'applique plus, temporairement.

**Comment le rétablir :** un token personnel Vercel valide, posé dans le secret
`VERCEL_TOKEN` du dépôt. La session CLI du poste est valide mais **expirant dans quelques
heures** — elle ne convient pas comme secret CI ; Vercel refuse par ailleurs qu'une session
CLI crée un token (`Cannot create tokens for this app`) : la création passe par le tableau
de bord. Soit le commanditaire crée le token lui-même, soit il s'authentifie dans l'onglet
Vercel du navigateur et l'agent le fait pour lui.

## 8. Le point à retenir

Une sauvegarde n'est pas un fichier qu'on a produit : c'est un fichier **qu'on a prouvé
rejouer**. La preuve tourne désormais chaque semaine dans la CI, avant la publication de
l'artefact. Le jour où la base devra être reconstruite, ce ne sera pas une inconnue : ce
sera un test déjà vert.
