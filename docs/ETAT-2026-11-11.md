# État réel du projet — contrôle du 11/11/2026

> Ce document est la réponse à « est-ce que le projet aboutit ? ». Il ne décrit pas une intention :
> il décrit ce qui a été **vérifié**, comment, et ce qui restait à corriger.
> Tous les contrôles ci-dessous ont été exécutés le 11/11/2026 contre la production et
> l'instance réelle.

---

## 1. Le verdict

**Le produit fonctionne.** L'application est en ligne, la base est publiée et saine, les tests
passent, le second facteur est actif et prouvé. Rien n'est « à moitié fait ».

Ce qui donnait le sentiment que le projet n'aboutissait pas, c'était **un trou dans la chaîne de
déploiement** : le projet Vercel n'était relié à aucun dépôt GitHub. Un `push` ne mettait rien en
ligne, et un déploiement refusé laissait l'ancienne version en service **sans le dire**. C'est
corrigé.

## 5. Comment rejouer ce contrôle

```bash
npm test                              # 34 tests du routeur
npm run deploiement:verifier          # configuration de déploiement
npm run base:verifier                 # instance réelle : 15 contrôles RLS
npm run mfa:enroller -- --verifier    # preuve aal2 sur les 5 rôles
npm run base:sauvegarder              # export hebdomadaire (nécessite SUPABASE_DB_URL)
```

Et, depuis GitHub : l'onglet **Actions** montre, pour chaque `push`, la recette, la vérification
de l'instance réelle et le déploiement.

---

## 6. Le piège à ne pas rejouer

Le refus du 06/11/2026 (*« the commit author doesn't have permission to create deployments »*)
vient de ce que Vercel compare l'**auteur du commit** à l'**adresse du compte qui déploie**. Ce
n'est pas un problème de code, et il est invisible : le déploiement est refusé, l'ancienne version
reste en ligne, et rien ne le signale.

La parade retenue : le déploiement passe par `--prebuilt`. Un artefact construit par la CI ne
porte pas de métadonnée git, et n'est donc jamais refusé. C'est aussi pourquoi `git config
user.email` doit rester l'adresse vérifiée du compte Vercel.
